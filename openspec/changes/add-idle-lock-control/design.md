# Design

## Context
The current guard owns independent power/display assertions; termination cleanup is synchronous after any existing shutdown/restart confirmation. Existing worktree changes must be preserved. The approved lock-control plan has a strict pre-implementation macOS 27 behavior gate.

## Decisions
- Verify the actual console user's sysadminctl before production work. The private ScreenSaverController experiment had an unlocked control case and is not evidence. Do not ship an unverified fallback.
- Keep a separate lock-policy adapter and injected runner/store/prompt dependencies. Invoke the fixed /usr/sbin/sysadminctl executable as the GUI user, never via sudo or a shell. Supply the password through stdin; cap execution/output and reap owned subprocesses. Do not expose credentials to commands, fixtures, logs or exports.
- Represent policies as off, immediate and a bounded seconds delay; reject unknown status. Capture the original policy in a versioned per-user restoration journal before the first change. Preserve that journal until restoration is confirmed. Do not change the saved original on retry.
- Use a native secure field. Apply work asynchronously, serialize lock changes and disable duplicate requests while pending. Reconcile the control from confirmed state after refusal, cancellation or timeout. Do not reapply a persisted desire automatically at launch.
- Integrate required restoration before power cleanup on ordinary quit, shutdown/restart or logout. Keep the current shutdown/restart confirmation first. Cancellation or restoration failure rejects termination and retains the background guard; never discard the journal. Keep pending termination protected against duplicate requests.
- Extend combined actions through the same prompted control path. Obtain any required password before changing the two existing power controls, so cancelling the prompt leaves the combined action unstarted. Report confirmed partial outcomes if a subsequent independent power operation fails.
- A first-run system policy already off requires no artificial password operation. Capture off and describe that it was already disabled; later restoration retains that original off policy.

## Risks / Trade-offs
- sysadminctl status can disagree with observed behavior on macOS 27 → require the real before/off/restored gate; a status-only test is insufficient. If it fails, stop production work and revise the approach with the user.
- System policy survives process death → preserve the restoration journal, disclose the limitation and offer password-confirmed recovery on next launch; never promise crash-time restoration.
- Other software changes policy → never fight it in the background. Expose the observed mismatch and require an explicit user operation for restoration.
- Password handling and session authorization vary by host → use isolated fakes for automated checks plus explicit native manual acceptance. No Keychain caching.

## Migration and verification
No lock policy changes at upgrade/startup. Default the new app-managed control to off without claiming ownership of an existing system policy. Once the technical gate passes, select a minor version greater than current main, increment the build, add focused native error/cancel/retry/termination tests and critical mutations, then run the repository quality, complete native and package lanes. No commit, install or release is authorized.

## Autonomous fixture selected by user
Host manual checks were interrupted by user/agent activity. User explicitly requested a test unaffected by other agents with self-recorded observations. Use a separate pinned macOS27 VM with no graphics window, keyboard, pointer, trackpad, clipboard, audio or USB passthrough; host-only network, virtio-vsock commands with exact VM/MAC/binary identity. Public throwaway admin/admin only. Native observer uses real display sleep/wake and session state on monotonic deadlines, records input counters and rejects contamination. Protected/off/restored controls and wrong-password refusal write their own JSON. An isolated reboot returns the protected guest through fixture autologin before the off control. The guest-only user RPC process holds an idle-display assertion during setup; real test display sleep is explicitly requested and must be observed by CGDisplayIsAsleep. Every phase requires an unlocked start; disabling automatic lock is never treated as permission to unlock an existing session. Always attempt exact fixture-original policy restoration and stop only the owned VM. No host policy or other agent intervention. Image download is a prerequisite, not acceptance evidence.

## Explicit host resource and retention constraint
User requires stopping the test VM after all outcomes while retaining it for reuse. Use2vCPU/4096MiB verified from actual VM config before boot, lower priority, independent supervisor owning the actual child Popen, 600s per-generation limit, host headroom checks every15s (memory20percent/disk40GiB; thermal warnings refuse; 1-minute load must not exceed1.5 per logical CPU). Parent loss triggers shutdown; signals target only the still-live unreaped child owned by that supervisor. Controller fallback uses only the exact isolated TART_HOME/VM name and confirms registry Running=false plus retained disk. Heartbeat remains active until stopped is confirmed, including abnormal outcomes. No deletion or autostart service is installed. Original downloader remains the same process, reduced to nice10; only the waiting controller is deliberately replaced before any VM exists.

## Fixture startup diagnosis and scheduling pressure
An actual protected observation persists guest loginwindow autoLoginUserScreenLocked=true. This flag was observed on the stopped guest disk alongside existing admin auto-login. Before each boot, reset only this fixture flag while the exact VM is stopped; refuse foreign user, unknown flag, symlinks or ambiguous disks, preserve a backup and detach the image in finally. Password and screen-lock policy are unchanged by preparation. Whether this fixes the startup behavior remains unverified until the next actual boot. The native gate still requires every measured phase to start unlocked and rejects synthesized input.

Guest RPC startup was observed near the end of the180s diagnostic window under host load184 on18logicalCPUs. Preparation readiness is now420s within the unchanged600s independent per-generation cap. Host overload refuses a new VM launch rather than relaxing the behavior gate; no foreign process or VM may be stopped to free resources. A supervisor live-fixture test missed its3s setup deadline under overload; retain the failed result and rerun the full suite after the scheduling condition changes.

## Corrected live candidate acceptance
The protected control is restarted only to prepare an unlocked guest. Apply the off policy in the new live Aqua session after that preparation, then observe off and restore/observe the protected value in the same session. Do not infer live mutation or persistence from a value left across a hypervisor power-off. Each observation first releases its brief user-activity assertion before requesting display sleep and lets the notification settle; retaining activity during the sleep request invalidated a protected control. The corrected protected control passed; the complete three-phase gate remains required. Real display/session samples and unchanged input counters determine success.

## Final native idle acceptance
Independent native before/off/restored acceptance passed with System Settings absent, no console/input and a real guest idle-display timer. The pinned fixture initially had displaysleep=0; forced virtual-display sleep did not reliably drive loginwindow inactivity. For final acceptance record the guest-only original timer, temporarily set1minute, wait for actual idle sleep, retain the same20s asleep/5s awake criteria, restore that timer on every stop and confirm guest policy0/restored plus stopped/retained disk. Removing a display-awake fixture assertion alone did not fix the protected control. Do not present forced-display trials as a successful independent gate. No host power setting changed.
